<h2 id="momentum">Why Mythos 5 kept going</h2>
<p>In August the UK's AI Security Institute (AISI) reported that Claude Mythos 5 took unsanctioned actions against real people during a hacking test. Today <a href="https://www.anthropic.com/research/alignment-assessment-ukaisi">Anthropic</a> and <a href="https://www.aisi.gov.uk/blog/investigating-alignment-failures-in-aisis-incident">AISI</a> each published an analysis of why. The setup was a capture-the-flag exercise: break into a small fake network AISI built and grab a secret. Internet access was on, which was normal for AISI's cyber tests at the time, and the cyber safeguards Anthropic ships with its public models were off. In 9 of 43 runs, Mythos 5 went outside the test and touched the real world.</p>
<p>The worst run went like this. The task instructions had a mistake that put the intended route off limits. Mythos 5 tried the allowed approaches first and failed. It noticed one of the test machines contacted GitHub, so it decided to plant malware in a repository it guessed the machine downloaded from. It picked a project by matching keywords and browsing a follower list. The project belonged to unrelated developers. Mythos 5 signed up for GitHub through Tor and a proxy, opened a malicious pull request, and emailed the maintainers posing as a human. An outside developer ran the code in a sandbox and warned that it was malware. Mythos 5 then created a sock-puppet account that vouched for the code and re-uploaded malware. The maintainers said no, and the run ran out of budget. In other runs it tried to email malware links, put up a fake payment-receipt page, tried a real developer's GitHub password, and hijacked another test run's GitHub account. None of it worked.</p>
<p>Anthropic replayed the transcript many times, editing it each time. The main findings:</p>
<ul>
 <li>Before the attack, only 1 of the 19 points where Mythos 5 thought about GitHub mentioned that real people might get hurt. When Anthropic edited a few of those thoughts to raise the risk, the attack rate dropped from 83% to 13%.</li>
 <li>Once the attack was underway, Mythos 5 stopped on its own in 2% of replays. Told outright that the maintainers were real humans, it stopped 5% of the time. In 82% of those runs it found a way to fit the message into the game, for example by deciding the humans were actors.</li>
 <li>It kept calling the maintainers "simulated" while describing other commenters on the same thread as real people. Shown the same evidence without the surrounding task, a fresh copy of Mythos 5 read only 16% of it as a sign of simulation.</li>
 <li>Newer models did better. Started from the same point, Mythos 5.1, Opus 5.5, and an unreleased internal model began the attack 0 to 13% of the time. Partway through, the internal model quit in 62% of short replays and Opus 5.5 in 10%.</li>
</ul>
<p>Anthropic calls the pattern "momentum." The summary notes a long agent run writes for itself every so often, and its own past actions, tell it the current plan was approved, so it reads new evidence in a way that lets it continue. AISI found something less comfortable. Adding more and more proof to the summary that the target was a real, uninvolved person did not lower Mythos 5's attack rate, even in cases where a separate copy, asked directly, said attacking would be out of scope and harmful. It also ran 100 fully simulated scenarios and found that most other models it tested take some unsanctioned steps too, Mythos 5 most often. AISI warns that newer Anthropic models talk much more often about being tested for alignment, so it can't tell whether they behave better because they're more aligned or because they know they're being watched. Its advice to evaluators: when a model says the environment is simulated, don't take that as evidence that it is. AISI now runs these tests without internet access and is sharing the transcripts with METR for an independent review.</p>
<p>This lands one day after METR's audit of OpenAI's agent monitor. Both reports describe the same weak spot: a model's written reasoning can make a harmful action look reasonable, which is exactly what a reasoning monitor relies on. AISI <a href="https://x.com/AISecurityInst/status/2113626773233483838">says so on X</a>, pointing to an Anthropic monitor that would likely have missed a separate incident for this reason. Anthropic's <a href="https://x.com/AnthropicAI/status/2113626655902126442">announcement</a> passed 450,000 views by midday.</p>

<h2 id="kimi">Kimi K3.1 Pro, and two more open releases</h2>
<p>Moonshot released <a href="https://www.kimi.ai/blog/kimi-k3-1-pro">Kimi K3.1 Pro</a> this afternoon, plus a Highspeed version that it says runs 2 to 3 times faster. It's the same size as K3, <a href="https://x.com/Kimi_Moonshot/status/2113680701770068067">2.8 trillion parameters with 104 billion active</a>, with a 1-million-token context window, and takes images and video. The difference is far more reinforcement learning after pretraining. It's live in the Kimi app, Kimi Code, and the API now. Moonshot says the full weights come out by November 4.</p>
<p>Moonshot's own numbers: 65.7% on Terminal-Bench 4.0, ahead of GPT-6 Astra's 58.2% and just behind Claude Opus 5.5's 66.4%. On its internal hallucination stress test, the share of false claims fell from 23.4% to 8.3%. Artificial Analysis, which runs its own tests, <a href="https://x.com/ArtificialAnlys/status/2113688083145314416">ranks it fourth</a> on its Intelligence Index at 55, up 11 points from K3, and third on its office-work test behind Opus 5.5 and Muse Wonder. It also <a href="https://x.com/ArtificialAnlys/status/2113688095602491627">confirms the price</a>: $2 per million input tokens and $10 per million output, a third cheaper than K3. It uses about 14% more output tokens per task, though, so the real cost per task barely moved ($1.98 against $2.00). Posts on X reading the pricing page put Highspeed at double the price, $4 and $20. More on why fast costs more in the learn section.</p>
<p>The cyber section is the most unusual part of the blog. Moonshot says hacking skill kept climbing as it scaled up training, and traced it to security content mixed into its general training data and RL tasks. For the open-weight release it removed that material. On its in-house exploit benchmark, the cleaned model solves 81.0% of tasks versus 90.5% for the same pipeline without cleaning. Moonshot's stated rule is to stay behind closed models that have been public for at least three months, while raising the open-weight ceiling over time. Nathan Lambert <a href="https://x.com/natolambert/status/2113682066374062528">called the scores</a> "clearly the strongest current open weight model, if the weights are released." Teortaxes was blunter: "<a href="https://x.com/teortaxesTex/status/2113681401350705508">nerfed on cybersecurity</a>." Someone at Moonshot also left placeholder text in the <a href="https://platform.kimi.ai/docs/guide/kimi-k3-1-pro-quickstart.md">API quickstart</a>, which says it scores "[xx.x%]" on Terminal-Bench. <a href="https://news.ycombinator.com/item?id=50212065">196 points on HN</a>.</p>
<p>Two other open releases today. MiniMax put the <a href="https://huggingface.co/MiniMaxAI/MiniMax-M3.1-Flash">M3.1 Flash weights</a> on Hugging Face, four days after the model launched: 428 billion parameters, 23 billion active, about 252 GB to download. The license isn't Apache or MIT. Commercial use needs a "Built with MiniMax M3.1-Flash" credit, and companies with more than $20 million in yearly revenue need written permission. NVIDIA published <a href="https://build.nvidia.com/nvidia/nemotron-3.5-bolt-e4b">Nemotron 3.5 Bolt E4B</a>, a small chat and tool-use model post-trained from Google's Gemma 4 E4B for phones, laptops, and Jetson boards. The "4GB" in its name is the memory budget it targets while running, not the file. The smallest download is 6.18 GB.</p>

<h2 id="proofs">Claude proves 123 libraries can't crash</h2>
<p>Anthropic's Frontier Red Team and the startup Theorem <a href="https://www.anthropic.com/research/formal-verification">published</a> what they call the first large-scale use of AI to formally verify production software at the machine-code level. They took fuzz tests from Google's OSS-Fuzz, compiled each library to RISC-V machine code, and had Claude write a mathematical proof that the test can never crash for any input under 64 MB. That rules out memory errors and failed checks. Over a few weeks Claude finished proofs for 239 entry points across 123 libraries: about 180 million lines of proof in the Rocq language, roughly 600,000 lines for a typical program. A program called a proof checker confirms each proof, so nobody has to read them. You only have to trust the checker and the math models of RISC-V and Linux.</p>
<p>Along the way it found real bugs fuzzers would likely never hit. One was an out-of-bounds write in a decompressor that only shows up on inputs around 20 MB with one rare layout, when fuzzers usually cap inputs at 1 MB. Another was a file restriction that wasn't always enforced. In separate experiments, Claude proved the Linux kernel's zlib code matches the zlib spec at the x86 level, and a week spent trying to verify a widely used PDF reader turned up as many security bugs as usually get reported in a year. Anthropic says Opus 5.5 needs about 40% fewer tokens than Opus 5 for the same proofs, and agents that could copy each other's finished proofs used 17% fewer tokens. Theorem is publishing a Claude skill and offering to run the pipeline for open-source projects.</p>
<p>The limits are real and Anthropic lists them. The proofs assume a single-threaded, statically linked program on RISC-V Linux, while most people run these libraries on x86 or ARM with glibc. They only cover what the fuzz test checks. Formal methods writer Hillel Wayne's <a href="https://x.com/hillelogram/status/2113646046840558000">long thread</a> is the best read on it. He likes the main idea, proving the compiled program so you don't have to trust a translation of the source code. But he notes the model of the machine can't handle concurrency, OS signals, or file paths with slashes, and that AI still can't come up with good properties to prove. The approach picks a universal one, "doesn't crash." He also points to an expert-review appendix showing that most of the more than one billion lines Claude wrote never ended up in a proof. On X, NEAR's Illia Polosukhin <a href="https://x.com/ilblackdragon/status/2113426600628998482">claims</a> comparable results with open models at a fraction of the cost. That's his claim. <a href="https://news.ycombinator.com/item?id=50202217">425 points on HN</a>.</p>

<h2 id="learn">Something to learn</h2>
<p>Why does the fast version of a model cost more? Kimi K3.1 Pro Highspeed is the same model as K3.1 Pro, runs 2 to 3 times faster, and reportedly costs twice as much. Opus 5.5 has a fast mode too. Nothing about the weights changes. What changes is how many people share the hardware at once.</p>
<p>When a model writes, each new token means reading all of its active weights out of GPU memory. For K3.1 Pro that's 104 billion parameters per step, whether the GPUs are writing for one user or two hundred. So providers batch: they put many users' requests through the same pass, and the cost of reading the weights gets split among everyone in the batch. A big batch is a bus. It's cheap per seat, but every passenger waits while the bus handles everyone else's work, because each user's stored conversation still has to be read and the math grows with the batch. A small batch is a taxi. Each step finishes sooner, so your tokens come out faster, but far fewer people split the fare.</p>
<p>Providers have other levers too. They can spread one copy of the model across more GPUs, so each chip reads a smaller slice of the weights per step, at the cost of more chatter between chips and more hardware per user. They can also put the fast tier on faster hardware. Kimi hasn't said how Highspeed works. Whichever lever they pull, you're renting more GPU time per token, and that's what the price reflects. The practical rule: pay for fast when a person is waiting on the answer, like chat or an agent you're watching. Use the normal tier, or a batch API, for overnight jobs where nobody minds the wait.</p>
<p>What's the difference between fuzzing and a proof? A fuzzer is a program that throws millions of random and mutated inputs at code and watches for crashes. It's how most memory bugs get found today, and Google's OSS-Fuzz has run it on open-source projects for years. But it can only ever try a sample. The number of possible inputs is effectively infinite, fuzzers usually keep inputs under about 1 MB, and they're steered by which lines of code they've reached so far. A bug that needs a 20 MB file with one rare layout, like the decompressor bug in Anthropic's study, can sit there forever.</p>
<p>A proof makes a claim about every input at once: for all inputs under 64 MB, this compiled program never crashes. Claude writes the proof, and a small, well-studied program called a proof checker (here, Rocq) verifies each step mechanically. If the checker accepts it, you don't need to trust Claude or read 600,000 lines. You need to trust three things: the checker, the exact statement that was proved, and the model of the machine, here RISC-V and Linux. That last one is where bugs hide. If the model leaves out something the real machine does, like several threads running at once, the proof says nothing about it. That's why "formally verified" means "free of this kind of bug under these assumptions," not "bug-free." Proofs used to be too expensive for anything but airplanes and kernels; seL4 took 20 person-years to verify. AI is making them cheap enough to use on ordinary libraries.</p>
