<h2 id="riemann">Lean's people sign off on the Riemann proof</h2>
<p>Yesterday's lead was a claim: Alpöge, a mathematician at Anthropic, said he and Claude had proved the Riemann hypothesis, and posted only Lean code. Today the <a href="https://leanprover-community.github.io/blog/posts/riemann-hypothesis/">Lean community blog</a> posted a joint statement from the Lean and Mathlib communities, endorsed by the Lean FRO and the Mathlib Initiative: "We have full confidence that Alpöge's proof of the Riemann Hypothesis is correct." They say the proof passes all four tests from Kevin Buzzard's checklist. The statement is Mathlib's own definition of RH. Dozens of people compiled the library and got the same proof export file. Two separate tools, <span class="mono">comparator</span> and <span class="mono">con-leche --compare</span>, confirmed the theorem proved is exactly that statement. And several separate checkers accepted the proof, including two, con-leche and con-ron, that come with their own formal proof that they can't accept a false proof. The checks ran on an exported copy of the proof, so any malicious code hidden in the Lean source couldn't interfere.</p>
<p>MIT's Andrew Sutherland keeps a <a href="https://math.mit.edu/~drew/grh/">page of the results</a>, run with Claude Code. All 175,187 modules compile with zero errors. The five main theorems rely only on Lean's three standard axioms. An independent kernel written in Rust, nanoda, accepted the full export in 27 minutes on 80 threads, and con-leche accepted all 1,468,418 declarations. When the page was last updated, at 7:55am ET, Lean's own kernel replay of the export and the end-to-end <span class="mono">lake comparator</span> run were still going. <a href="https://www.scientificamerican.com/article/the-ai-riemann-hypothesis-proof-is-almost-certainly-true-independent-mathematicians-attest/">Scientific American</a>, in an update today, says the comparator run is now done, and quotes Sutherland: "Honestly the chance that anything is fishy here is approximately zero."</p>
<p>What this doesn't settle is understanding. The statement ends by looking forward to work "that will help explain the new ideas in this proof," and Daniel Litt <a href="https://x.com/littmath/status/2123872779833688078">posted</a> that "Math would be a lot more fun right now if the models were better at exposition!" The Clay Institute hasn't said anything, and its rules require two years after publication before a prize. Today's thread on <a href="https://news.ycombinator.com/item?id=50589618">Hacker News</a> passed 480 points.</p>

<h2 id="inkling">A 26B model that loops</h2>
<p>Thinking Machines, Mira Murati's lab, <a href="https://thinkingmachines.ai/news/inkling-2-mini/">released Inkling 2 Mini</a> yesterday with open weights under Apache 2.0. It's a mixture-of-experts model with 26.4B total parameters and 3.4B active on each pass. The trick is looping. Per <a href="https://huggingface.co/blog/inkling2mini">Hugging Face's writeup</a>, the model has 24 layers. Layers 0 to 5 run once, layers 6 to 17 run three times with the same weights, and layers 18 to 23 run once, for 48 layer visits per token. Each pass reads a small "message" from the previous one, so it refines the last pass instead of repeating it. That works out to 5.4B active parameters per token while storing only the 24 layers. Weights ship in NVFP4, with the last four layers in MXFP8, for about 20 GB total. The lab ran it in airplane mode on a 48 GB MacBook Pro.</p>
<p>The numbers are good for its size. Thinking Machines says it leads open models under 100B on DeepSWE v1.1 at 48.2%, and reports 79.2% on SWE-bench Verified. <a href="https://x.com/ArtificialAnlys/status/2123877871316087012">Artificial Analysis</a> puts it at 20 on its Intelligence Index, tied with Alibaba's dense Qwen3.8-27B, and <a href="https://x.com/ArtificialAnlys/status/2123877878568001635">says</a> it costs $0.59 and takes 9 minutes per index task, against $3.53 and 38.2 minutes for Qwen. The limits are honest in the post. Looping helps reasoning but doesn't store more facts, so it scores like other models its size on factual recall. Running more of its thinking inside the loop instead of writing it down could make it harder to monitor, so the lab released a variable-loop research model to study that. In its tests, chain of thought got shorter with more loops but stayed readable. The <a href="https://news.ycombinator.com/item?id=50581260">Hacker News thread</a> hit 1,260 points, and <a href="https://venturebeat.com/technology/thinking-machines-wows-with-inkling-2-mini-looped-transformer-model-that-runs-locally-on-laptops">VentureBeat</a> says Unsloth has GGUF builds aimed at 16 GB machines.</p>

<h2 id="simplebench">GPT-6.2 slips on trick questions</h2>
<p>SimpleBench is a set of 200-plus multiple-choice questions about space, time, social sense, and misleading wording, where nine ordinary people averaged 83.7%. <a href="https://traictory.com/news/2026-11-20-gpt-6-2-astra-simplebench-regression">Traictory</a> went through the updated board. GPT-6.2 Astra scored 77.3%, down from 83.6% for GPT-6 Astra and now under the human baseline. GPT-6.2 Sol fell 13 points to 69.9%. Claude Fable 5.2 leads at 94.9%, with Gemini 4 Neon at 94.4%. Each score is an average of five runs at temperature 0.7, so small gaps don't mean much, but 13 points is not small. Artificial Analysis, Traictory notes, had Astra flat and Sol down three points on its own index. The likely story is a training mix tuned for long agent loops with many retries, which SimpleBench doesn't reward. The <a href="https://news.ycombinator.com/item?id=50588916">Hacker News thread</a> is up today.</p>

<h2 id="learn">Something to learn</h2>
<p>What does it mean to cut two-thirds of a model's experts and then "heal" it? A mixture-of-experts model splits each layer's feed-forward part into many small networks, the experts, plus a router that picks a few for each token. Inkling 2 Mini picks 8 per layer. It started training with 384 experts per layer. Partway through, Thinking Machines <a href="https://thinkingmachines.ai/news/inkling-2-mini/">says</a>, it deleted two-thirds of them, keeping the 128 the router used most in each layer. Why bother? A model's file size depends on all of its experts, even though each token only uses 8. Cutting 256 per layer cuts most of the file, which is what lets it fit on a laptop, while the work per token stays about the same. But the router had been sending some tokens to the deleted experts, so right after the cut the model is worse. Healing is extra training to fix that. Here they trained on 1 trillion tokens of output from a larger Inkling model, which is distillation, so the 128 survivors learned to cover the work of the ones that were cut. The lab says that got the model back to where it was before the cut, then it went on to normal fine-tuning and RL. Why not just train with 128 from the start? The post doesn't say, but a likely reason is that more experts early on give the model more room to learn, and the router's use counts then show which ones are safe to drop. The general lesson is that size, speed, and quality are separate choices. Pruning shrinks the file, looping adds compute per token without adding weights, and 4-bit weights shrink it again.</p>
<p>And what's a double free, the GnuPG bug? Programs written in C ask for memory with malloc and hand it back with free. The allocator keeps a list of free blocks so it can reuse them. Call free twice on the same block and the block can go on that list twice. Then two later requests for memory can both get the same block, so two unrelated parts of the program are writing to the same memory without knowing it. An attacker who controls what gets written can use that to corrupt the allocator's bookkeeping, which is often a step toward running their own code. GnuPG's <a href="https://lists.gnupg.org/pipermail/gnupg-announce/2026q4/000517.html">advisory</a> explains how this one happened. GPGME reads gpg's output into a 1,024-byte buffer and moves it to a bigger buffer if a line is too long, which frees the old one. The function kept using the new pointer but only saved it back to the shared context at the end. If it returned early on an error, the context still held the old, already freed pointer, and freeing the context later freed that block a second time. A crafted key with a very long user ID is enough to force the move. Allocators often check for double frees, but GnuPG notes that the other allocations in between can slip past those checks. It's a cousin of the use-after-free covered here last month: the bug in both is a pointer that outlives its memory. The fix is one line, saving the new pointer right away.</p>
